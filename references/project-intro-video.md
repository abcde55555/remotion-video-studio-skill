# 产品 / 功能介绍片 SOP（非走查版）

> 范围：产品、模型、功能、发布会概念片、技术分享片——以脚本/口播/动效卡片为主。
> **不适用**于 GitHub 开源项目介绍：那类走「真实页面走查」（repo 全页截图 + 推拉/滚动/点击），见 `references/open-source-intro-sop.md`。

用于「介绍一个产品/工具/模型能力」的视频：观众是开发者或技术决策者，目标是让他们理解「它是什么、怎么用、边界在哪」。

## 与新闻/发布片的差异

| 维度 | 新闻片 | 项目介绍片 |
|---|---|---|
| 观众 | 路人 | 开发者/潜在用户/贡献者 |
| 目标 | 知道发生了什么 | 判断能力、可信度、上手成本 |
| 叙事 | 新闻锚点→亮点→收尾 | 问题→洞察→方案→证据→架构→边界→上手 |
| 文案 | 口语为主 | 术语准确 + 短句；命令/版本/参数直接上屏 |
| 证据 | 官方 demo、数字 | 架构图、代码/命令、基准、真实运行、测试数 |
| 结尾 | 情绪/口号 | 3 条命令 + 链接 + 判断 |

## 参考片实测（2026-11 样本）

| 视频 | 时长 | 语速 | 视觉节奏 | 关键手法 |
|---|---|---|---|---|
| Fireship 100s 系列 | 131s | 415 wpm | ~4s/屏 | 代码高亮 + 2–4 词大字关键词 + 梗图 |
| 项目速览（README 滚动） | 66s | 344 wpm | ~5–8s/段 | 屏幕录制 + 高亮 + 底部字幕 |
| 实测评测 | 239s | 335 wpm | ~8–12s/段 | 自测 + 分数 + 揭短反转 |
| 作者自述 | 295s | 335 wpm | ~10–15s/段 | 反直觉数字（7MB vs 400MB）+ 取舍 |

结论：中文项目片目标 **230–280 字/分**（90s ≈ 350–420 字）；**每 2–5 秒一个视觉事件**（切屏/高亮/放大/数据出现），90s 内 25–40 个；钩子 = 反直觉结果 + 数字 + 揭短承诺；必须有自测（分数/耗时/失败点）。

## 8 段骨架

1. 一句话是什么（谁/解决什么/用什么做的）
2. 为什么现在值得看（差异化）
3. 它怎么工作（3–5 步闭环 + 流程图）
4. 证据 1：能跑（真实 demo + 环境/版本）
5. 证据 2：有数据（基准/测试/性能；没有就说没有）
6. 架构/技术选择（给能看代码的人）
7. 边界与风险（alpha/限制/法律/安全）
8. 怎么开始（命令 + 最小示例 + 文档）

## 文案规则

- 术语首次出现 5 字内解释（「clean room——不读源码，只看外部可见行为」）。
- 每个技术点配「所以呢」。
- 命令/版本/平台/License 上屏，不口播念全。
- 对比只给可核实维度，不做「最强」。
- 主动说边界；每 20–30s 给一张可截图卡片。

## 信息密度（比新闻片更严）

| 指标 | 目标 |
|---|---|
| 每屏信息点 | 8–12（含代码/命令/参数） |
| 每分钟有效事实 | 45–60 |
| 静音可读率 | ≥90% |
| 纯空镜 | 0 |
| 可带走资产 | 架构图 + 命令清单 + 对比表 + 链接 |

## 证据规则

- 每个「能」都要有截图/录屏/命令输出/测试数/Release 链接。
- 区分「官方声称」与「我验证」；没验证写「README 称」。
- 版本/日期/平台进角标，避免过期。

## 素材

- 仓库 `docs/images/*`、README 截图、Release 页、目录树、CLI 录屏。
- 架构图优先重绘（矢量/HTML），不用模糊截图。
- 标注「官方截图/官方素材」；许可证与免责声明核对。

## QA 增项

- [ ] 技术事实逐条对 README/docs/Release（版本/平台/许可/数量）
- [ ] 命令可复制可运行
- [ ] 演示环境写明（OS/版本/是否需要 key）
- [ ] alpha/限制/法律声明在片内
- [ ] 无绝对化表述，对比维度可核实

## 推荐结构比例（90s）

钩子 8s｜是什么 12s｜差异化 14s｜怎么工作 16s｜验证 14s｜技术底座 14s｜边界 8s｜上手 4s。


## 严谨实测（预注册）

宽泛横向评测成本高且变量不可控；优先做「单案例深测」：

- 目标：自有站点/项目（版权干净、可公开前后对比）。
- 固定：环境（OS/浏览器/CLI 版本/日期）、提示词、运行方式；每个模式跑 2 次，看波动。
- 指标：Study/Build/Check/总耗时、likeness 分数、差异项、失败项、费用、两次差异。
- 公开产物：capture.json、checks/、截图、项目文件、日志（可复核）。
- 声明未测项：目标数、builder 版本、日期；不做「所有网站都行」的结论。
- 想省成本可做 study-only 反向用法（只用它读懂项目，不重建），但片内必须标注「未完整重建」。


## 中国平台（B 站/小红书/抖音）观察（2026-11 样本）

B 站 12 条 + YouTube 中文 3 条实测：

| 时长 | 作用 | 结构 | 典型播放 |
|---|---|---|---|
| 30–60s 竖屏 | 拉新 | 圈内钩子 + 一个卖点 + CTA | 低 |
| 2–3min | 上手 | 痛点 → 方案 → 区别/类比 → 版本/安装 → 演示 → 反馈 | **最高**（解决安装门槛） |
| 12–15min | 信任 | 四问清单 → 定义 → 类比 → 实测 → 安全/翻车 → 回到四问 | 中 |

观众关注点（按评论区频率）：
1. 有没有真跑一次（「差个实车落地」）
2. 安装/版本门槛（版本号、依赖、3 个坑）
3. 成本/token
4. 安全（npm install 执行脚本、系统调用）
5. 与竞品区别（如 REA：拆零件 vs 隔着橱窗看）
6. 分数可信度（改名换配色扣分）
7. 版权/合法
8. BGM/节奏（信息优先，音乐压低）

高密手法：问题清单开场、对比表、真实计时器、版本/环境卡、翻车镜头、官方数据 vs 自测分栏、成本卡、适合/不适合两列。

钩子套路（中立化使用）：热度数字（「6 天半 1.8 万星」）、对比锚点（「vs REA」）、揭秘（「上了两台秤」）、上手（「装前先对版本号」）。
